## 背景

控制台是主窗口底部区的左侧面板（右侧为实时 logcat Tab），承担**应用级运行信息**的展示：
命令回显（`> adb ...`）、操作结果（`[拉取成功]`）、错误提示（`[错误] 未选中设备`）。
对应 Python 版 `BottomWindow` 的控制台 Tab。

本文档描述其实现方案。核心问题：**非 UI 世界（协程、回调、子进程管理代码）如何向
UI 世界（Compose 树）单向喂数据**——由 `createLogFlow` 的桥接模式回答（§1）。

## 1. LogFlow 讲解：业务层打印如何送达 UI 展示

`createLogFlow`（ConsolePanel.kt）只有 15 行，却是整个控制台的枢纽。
它在 `Main.kt` 装配处创建，进程级存活：

```kotlin
val (consoleLogFlow, logAppender) = createLogFlow()
```

### 1.1 它解决什么问题

- 应用里所有"该给用户看"的运行时信息产生于**任意线程、任意时机**——`scope.launch`
  里的 IO 协程、`ScreenRecordDialog` 的回调、`TransferCenter` 的传输线程……
- 这些地方拿不到任何 Compose 的引用（也不该拿——依赖方向上 core 不能依赖 ui）；
- 但最终要显示在 `ConsolePanel` 这个 Composable 里。

`createLogFlow` 就是中间的**桥**：返回"读端 + 写端"一对，读端给 UI，写端给业务代码。

### 1.2 逐行拆解

```kotlin
fun createLogFlow(): Pair<MutableStateFlow<List<LogEntry>>, (String, Int) -> Unit> {
```

**返回类型本身就是设计声明**。写端被刻意声明为 `((String, Int) -> Unit)` 而不是
`MutableStateFlow<...>`——虽然类型系统不阻止用 flow 去写，但签名上只暴露函数意味着：

- 写端拿到的是"只能追加一条日志"这个**最小能力**；
- 无法从写端清空、替换、读取整个列表；
- 拿到它的 `CustomActionHandler`、`TransferCenter` 等业务代码天然被限制在
  "说一句话"的权限内。

这是接口收窄（capability narrowing）。对比：若直接把 `MutableStateFlow` 传出去，
任何持有引用的代码都能 `flow.value = emptyList()` 或塞垃圾数据，约束只剩口头约定。

```kotlin
val flow = MutableStateFlow<List<LogEntry>>(emptyList())
```

选 `MutableStateFlow` 而非 `SharedFlow`/`Channel`，三个原因：

1. **状态语义**——控制台显示的是"当前日志全量"，新订阅者（Tab 切回来、窗口重建）
   要立刻看到已有内容，`StateFlow.value` 天然带状态回放；`SharedFlow` 默认不 replay，
   切个 Tab 日志就没了。
2. **合并（conflation）语义**——`StateFlow` 更新"只关心最新值"，UI 重组频率跟不上
   日志产生频率时中间态自动跳过，不会积压。控制台恰恰不在乎丢掉中间重组帧。
3. **`collectAsState()` 一线直达 Compose**：`val logs by logFlow.collectAsState()`，
   每次 `flow.value = ...` 后所有读这个 state 的 Composable 自动重组。

`List<LogEntry>` 是不可变数据类列表——每次追加都产生新列表（见 1.4 代价分析）。

```kotlin
val timeFormatter = DateTimeFormatter.ofPattern("HH:mm:ss")
```

闭包内持有一个 `DateTimeFormatter`（线程安全、immutable），多协程并发调 appender
不会出问题；避免每条日志重复解析格式串。标准的"构造一次、闭包复用"。

```kotlin
val appender: (String, Int) -> Unit = { message, level ->
    val timestamp = LocalTime.now().format(timeFormatter)
    val entry = LogEntry(timestamp = timestamp, message = message, level = level)
```

时间戳在**写入时**定格。若只存 message、显示时再取当前时间，日志列表重组重渲染时
每条的时间会漂移。`LogEntry` 是纯数据快照，渲染多少次结果都一样——幂等渲染是
Compose 声明式 UI 的基本要求。

`level` 参数取值 0–5，映射到 `logColor(level)`（Color.kt）主题色：
0/1→LogDebug、2→LogInfo、3→LogWarn、4→LogError、5→LogStamp。

```kotlin
    flow.value = flow.value + entry
```

**读-改-写整体替换**。`flow.value + entry` 返回新列表（拷贝旧的全部元素 + 新元素），
然后原子替换 `StateFlow.value`。一个正确的性质、一个真实的代价：

- **正确性**：UI 协程读到的任何列表版本都是完整一致的快照，不会看到"加了一半"的
  列表。`StateFlow.value` 赋值本身是原子（AtomicReference）语义，`collectAsState`
  收到的每个值都是可用状态。
- **代价（已知弱点）**：`+` 是 O(n) 全量拷贝。日志到 2000 条时每追加一条要拷 2000
  个引用。控制台低频写入（每秒几条顶天）完全无感；但不能拿这个模式做高频流——
  **这正是 logcat 实时 Tab（`LogcatStream`，core/logcat）不复用它、而用
  `SharedFlow + DROP_OLDEST` 环形缓冲的原因**。两个组件长得像，但服务于完全不同的量级。

**并发注意事项**：`flow.value = flow.value + entry` 不是读-写合并的原子操作，两个
线程同时 appender 理论上可能互相覆盖（都读到旧列表、各自追加、后写的赢，丢一条）。
若未来出现多线程并发汇报场景（如多个传输任务同时完成），应换用
`flow.update { it + entry }`（CAS 重试，线程安全）加固。当前写入方多为协程内串行调用，
未触发。

```kotlin
    if (flow.value.size > 2000) {
        flow.value = flow.value.takeLast(1500)
    }
}
```

**两级容量控制**，防内存无限增长。"超 2000 一次砍到 1500"的锯齿策略：`takeLast(1500)`
是一次 O(n) 拷贝，但每 500 条才发生一次，均摊可忽略。

留 1500 而非清空的原因：清空会让用户看到日志"周期性消失"；砍最旧 500 条时视口内
（用户在看底部）的内容基本不动，LazyColumn 的 key diff 只需移除顶部项。

### 1.3 数据流全景

```
业务代码（任意线程）                    UI 世界
┌──────────────────────┐           ┌──────────────────────────────┐
│ logAppender(msg, 4)  │           │ ConsolePanel(logFlow)        │
│  ↓ 闭包捕获           │           │   logs by collectAsState()   │
│  LogEntry(时间,文,级)  │           │   ↓ value 变化 → 重组         │
│  flow.value = 新列表   │ ─StateFlow→│   LazyColumn 渲染列表尾部     │
│  超限裁剪             │           │   logColor(level) 着色        │
└──────────────────────┘           └──────────────────────────────┘
      写端（无 Compose 依赖）             读端（无业务依赖）
```

两个架构性质：

1. **写端零依赖**。`(String, Int) -> Unit` 不引用任何 ui 类型，所以 `TransferCenter`
   （core 层）能持有它而不违反"core 不依赖 Compose"的红线。本质是**手写的依赖倒置**：
   core 定义不了 UI 日志长什么样，但接受一个"汇报出口"。
2. **进程级生命周期**。flow 与 appender 在 `main()` 里创建、进程级存活（不像
   Composable 的 state 随组合生灭），控制台内容跨窗口重建、跨 Tab 切换健在。
   清空操作走 `logFlow.value = emptyList()`（ConsolePanel 清空按钮）——清空是
   **读端**直接改 flow，这就是参数名是 `logFlow: MutableStateFlow<...>` 而非只读
   `StateFlow<...>` 的原因：UI 需要"清空"这个写能力，但它是受限的（面板自己的
   按钮触发）。

### 1.4 设计取舍总结

| 决策 | 得 | 失 / 边界 |
|---|---|---|
| `StateFlow<List>` 全量快照 | 新订阅者即见全量；UI 幂等渲染 | 每条 O(n) 拷贝——不适合高频流（logcat 走 `LogcatStream`） |
| appender 收窄为函数类型 | 业务端最小权限、core 层可用 | 失去背压/结构化取消（fire-and-forget） |
| 写入时定格时间戳 | 渲染幂等 | 无 |
| 裸 `flow.value =` 赋值 | 简单 | 多线程并发写可能丢条——可换 `flow.update {}` 加固 |
| 锯齿式 2000→1500 裁剪 | 均摊开销低、视口稳定 | 超过 1500 的旧日志不可恢复 |

一句话总结：`createLogFlow` 用**"不可变快照 + StateFlow + 最小权限写端"**换来一个
跨层、跨线程、零 UI 耦合的控制台管道——代价是全量拷贝，因此刻意只服务于低频的
应用级日志，高频的 logcat 另起炉灶。这两者的分界是本设计最值得记住的判断。

### 1.5 与文件日志（appLogger）的关系

`logAppender` 之外还有一条独立的日志通道：`AppLogger`（slf4j，落
`desktop-app/logs/easyadb.log`）。两者分工：

| | consoleLogFlow（本方案） | appLogger（文件日志） |
|---|---|---|
| 受众 | 用户（UI 上实时看） | 开发者（事后排查） |
| 生命周期 | 内存 2000 条，随进程消失 | 磁盘持久，跨会话 |
| 内容 | 命令回显、操作结果、面向用户的提示 | 内部状态、异常堆栈、命令全量 |
| 写入方 | 显式 `logAppender(msg, level)` | `logger.info/error {}` |

部分关键命令（如 `AdbExecutor.execAdbArgs`）会**双写**：logger 落文件供排查，
logAppender 上屏供用户确认。
