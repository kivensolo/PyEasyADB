# 实时日志（Logcat 面板）数据记录、清理与查找机制方案

> 版本：v2.0.0（分支 `dev/v2.0.0_cmp`，提交 `a7c8c44`，2026-09-17）
> 涉及代码：`cmp/core/adb/src/main/kotlin/com/easyadb/core/adb/LogcatStream.kt`（数据层）、
> `cmp/ui/logcat/src/main/kotlin/com/easyadb/ui/logcat/LogcatPanel.kt`（展示层）
> 对应 Python 原版：`utils/ADBTools.py` 的 `LiveLogAdbThread` + `LogCatFilter`、`src/widget/BottomWindow.py` logcat 标签

---

## 1. 背景与目标

Python 版实时日志的三个核心问题，构成本方案的设计输入：

| Python 版行为 | 问题 |
|---|---|
| `LiveLogAdbThread` 阻塞读子进程输出 | Compose 直译后读循环跑在收集方（UI）上下文上，logcat 启动倾泻历史缓冲（数千行瞬时到达）直接把 UI 线程占死——**点启动整窗卡死**（v2 首版实测） |
| `LIVE_LOG_COUNTS_LIMITS = 3000` 条数上限 | 条数是糟糕的内存代理指标：行长 50 与 500 字符的 3000 条内存差 10 倍，既浪费（限制过死）又不精确 |
| `LogCatFilter` 发射前过滤 | 只对新到达的行生效，切换级别/关键字不重刷已显示内容，体验上等于没有过滤 |

目标：

1. **不卡 UI**：任何日志速率下主线程零阻塞；
2. **容量按内存预算管理**：默认给固定 KB 预算（8MB），后期可经设置功能注入；
3. **过滤即时生效**：切条件立即重滤已缓冲内容，且被过滤的行不丢失、可恢复；
4. **支持查找**：Ctrl+F 查找工具条，计数 / 前后跳转 / 行内高亮，对标 Android Studio logcat。

## 2. 总体架构：数据管道

```
adb -s <ip> logcat -v time          子进程
        │  stdout 逐行
        ▼
┌─ LogcatStream.logcatFlow（callbackFlow）──────────────────────────┐
│  launch(Dispatchers.IO)：                                         │
│    readLine → regex 解析 pid/level → seq 自增 → trySend(entry)    │
│  awaitClose { destroyForcibly() }   ← 取消即杀进程                │
└───────────────────────────────────────────────────────────────────┘
        │  Flow.buffer(1024, DROP_OLDEST)   ← 消费不过来丢最旧
        ▼
┌─ LogcatPanel：collect 攒批 ───────────────────────────────────────┐
│  pending 批 + 150ms 定时 flush：                                   │
│    1. LogcatBuffer.append(pending)     全量入环，超预算头部淘汰    │
│    2. 显示视图同步（淘汰剔除 + 通过过滤条件的新行追加）             │
│    3. Find 索引增量维护（只扫新批 + 剔除被淘汰匹配）                │
└───────────────────────────────────────────────────────────────────┘
        ▼
  LazyColumn（SnapshotStateList 增量更新，虚拟化只组合可见行）
```

职责划分：**数据层（core:adb）只管"进程 ↔ 条目流 ↔ 全量缓冲"**，不理解过滤条件；
**展示层（ui/logcat）持有过滤/查找状态，派生显示视图**。过滤条件是 Compose 状态，
条件变化驱动重滤——这是"切条件立即生效"的机制根基。

## 3. 日志数据记录机制

### 3.1 发射端：全量流（LogcatStream.logcatFlow）

- 子进程经 `cmd.exe /c adb -s <ip> logcat -v time` 启动；读取循环固定跑在
  `launch(Dispatchers.IO)` 上——**callbackFlow 的 block 运行在收集方上下文**，直接在
  block 里 `readLine()` 会挂住收集方线程（v2 首版卡死的根因）。
- 每行用 `LOGCAT_PATTERN` 正则解析出 `pid` / `level`（无法解析按 `pid=-1`/`INFO` 兜底），
  构造 `LogcatEntry(seq, raw, pid, level)` 发射。**发射端不做过滤、不做格式化**——
  level/pid 随条目携带，为展示层"零 regex 重滤"埋点。
- **seq**：`AtomicLong` 单调自增，随条目发出，永不复位（清空显示、停止重启都不复位）。
  用途见 §3.3。
- 背压：`Flow.buffer(1024, DROP_OLDEST)`——UI 消费慢时丢最旧，进程侧永不积压。
- 退出路径：收集方取消（停止按钮/面板销毁）→ `awaitClose { proc.destroyForcibly() }`
  立即杀进程，阻塞中的 `readLine()` 随之返回；进程自然退出后读取 stderr，把设备离线等
  报错作为一条 `ERROR` 级条目发出。

### 3.2 数据结构：LogcatEntry

```kotlin
data class LogcatEntry(
    val seq: Long,      // 单调序号：一切"按内容定位"的锚点
    val raw: String,    // 原始行文本
    val pid: String,    // 解析出的进程号（未解析为 "-1"）
    val level: LogLevel // V/D/I/W/E
)
```

刻意不存派生物（无着色 HTML、无时间戳副本）：着色由 UI 层 `LogColor.byLevel` 现算，
单条内存压到 ~350B（典型 ~120 字符行：raw ≈ 144B + pid/level/对象头/队列槽位 ≈ 200B）。

### 3.3 为什么需要 seq：位置漂移

预算缓冲不断从**头部淘汰**旧行，列表位置（下标）持续漂移：

- 匹配索引若按下标记录，淘汰一批后全部错位；
- LazyColumn 用内容（pid/文本）做 key 会在重复行（logcat 很常见）下撞重复 key 崩溃，
  用下标做 key 则头部淘汰时全列表错位、无法增量更新。

seq 单调唯一，是唯一稳定锚：LazyColumn 的 item key、Find 的匹配与跳转、淘汰同步阈值
全部基于 seq。**子序列性质**：显示视图与 Find 索引都是"全量缓冲按 seq 升序的子序列"，
所以对它们做二分查找始终成立。

### 3.4 攒批与刷新（LogcatPanel）

日志条目先进 `pending` 批，150ms 定时 flush——逐条写状态在倾泻期（数千行/秒）会触发
重组风暴。flush 做三件事（顺序执行，都在 Main 协程上，与其它状态写天然互斥）：

1. `LogcatBuffer.append(pending)`：全量入环 + 预算淘汰；
2. 显示视图增量同步（§5.2）；
3. Find 索引增量维护（§6.3）。

流结束/取消时在 `finally` 里补一次 flush + `stop()` + `isRunning` 复位，保证设备掉线
不残留"运行中"假状态、尾批不丢。

## 4. 日志清理机制

清理有四条路径，全部以 seq 为阈值，绝不按下标/条数：

### 4.1 预算淘汰（自动，LogcatBuffer.append）

- **字节预算制**：默认 8MB（`DEFAULT_BUDGET_BYTES`），`LogcatStream(budgetBytes)`
  构造参数注入——后期设置功能只需传入用户值，内部零改动。
- 每条估算 `raw.length × 2 + pid.length × 2 + 96B`（UTF-16 字符 + 对象/队列槽位摊销，
  **保守估算**：Latin-1 紧凑字符串实际只占 1B/字符，真实占用只低不高，预算不会被击穿）。
- `append` 时累计，超预算从最旧开始弹出直到达标；`while` 条件带 `size > 1` 兜底，
  保证单条超预算的病态长行也至少保留最新一条。
- 为什么不用条数上限：条数无法稳定表征内存（行长浮动 10 倍）；而 LazyColumn 虚拟化下
  渲染成本只与可见行数（~30 行）相关，**总量的唯一约束就是内存**——字节预算才是正确的
  代理指标。8MB ≈ 1.5~2.4 万行，约为旧 3000 条上限的 6~8 倍，JVM 堆增量无感。

### 4.2 显示视图同步清理（flush 内）

显示视图是全量缓冲的**过滤子序列**，视图行数 ≠ 缓冲行数，不能按淘汰条数删。做法：
取 `buffer.oldestSeq()`，把视图头部 `seq < oldestSeq` 的前缀剔除（视图按 seq 升序，
前缀扫描即可），再追加新批中通过过滤条件的条目。

### 4.3 Find 索引同步清理（flush 内）

`matchSeqs.dropWhile { it < oldestSeq }`——被淘汰的匹配直接出索引；若当前匹配
（`currentMatchSeq`）也被淘汰，跳转逻辑沿方向取最近存活匹配（§6.4）。

### 4.4 手动清空（右键菜单/工具栏按钮）

`clearDisplay()`：清 `LogcatBuffer` + 清显示视图。**过滤条件与 Find 状态不受影响**，
seq 计数不复位（历史 seq 依然唯一，无需分代）。

## 5. 过滤视图机制（记录与展示的桥梁）

### 5.1 条件即状态，视图即派生

过滤条件（`selectedLevel`、`searchText`）就是面板的 Compose 状态，显示列表
`logEntries`（SnapshotStateList）是全量缓冲按当前条件派生的子序列：

- **条件变化 → `LaunchedEffect(selectedLevel, searchText)` 全量重滤**：从
  `buffer.snapshot()` 过滤出派生列表，整体替换视图；重滤只有数值比较 + `contains`
  （level/pid 发射时已解析好，**零 regex**），2 万条毫秒级，主线程同步完成无感。
- **flush 增量**：新批只按当前条件过滤追加，不重扫全量。
- **被过滤的行仍在全量缓冲里**，切回条件即恢复——这是"过滤视图"与 Python 版
  "前置丢弃"的本质区别（Python 的 `logCache` 历史重滤能力，以此形态回归）。

### 5.2 一致性保证

重滤 effect 与 flush 协程都在 Main 派发器上，且各自正文无挂起点——二者交错只发生在
协程调度边界，单次执行内对 `logEntries` 的读写是原子的，无需额外同步。重滤快照取自
`buffer.snapshot()`（引用拷贝，~160KB/次，交互频率下可忽略）。

### 5.3 代价与权衡

8MB 从"只存过滤后"变为"存全量"：高过滤强度下（如只看 ERROR）可见行数少于
"8MB 全 ERROR"的极端值，换来的是条件可逆。日志视图的定位是"看最近发生了什么"，
更早的历史应落盘（`logcat -f`）而非加大内存，这是产品边界。

## 6. 查找机制（Find 工具条）

### 6.1 交互定义

- **Ctrl+F** 打开顶部 FindBar（已打开则重新聚焦）；**Esc** 关闭并清高亮；
- **Enter / Shift+Enter** 下一个 / 上一个；到头**回绕**（最后一个→第一个）；
- 计数 `cur/total`，流式运行中显示 `cur/total+`——`+` 表示匹配总数随新日志持续增长
  （total 由增量扫描实时累加，不是快照值）；
- v1 从简：大小写不敏感包含匹配，无正则/大小写开关（预留）；
- 查找作用域 = **当前过滤视图**（过滤与查找自然叠加）；查找激活期间自动滚动让位，
  不把视口拽回底部。

### 6.2 匹配索引：seq 锚定

```
matchSeqs: List<Long>       // 升序，过滤视图中所有命中行的 seq
currentMatchSeq: Long?      // 当前选中匹配的 seq（不是下标！）
```

用 seq 而非下标记"当前匹配"：缓冲淘汰、条件重滤都会让下标漂移，seq 在任何增删后仍然
有效，回绕/相邻计算永远用二分（列表升序）完成，无需维护任何索引算术。

### 6.3 索引维护：全量 + 增量双路径

- **查询词变化**：去抖 200ms 后对过滤视图全量扫描（`contains` 2 万条毫秒级），
  重建 `matchSeqs`；当前匹配仍命中则保持不变，失效则自动选中首个并跳转。
- **flush 增量**：只扫新批 `pending`，命中追加到 `matchSeqs` 尾部（新批 seq 必然大于
  现有全部匹配，追加即有序）；同时按 `oldestSeq` 剔除头部被淘汰的匹配。
- **条件重滤联动**：派生视图重建后，Find 索引基于新视图整体重建（查找语义 =
  "在过滤结果内查"自动成立）。

### 6.4 跳转：二分定位 + 失效回退

```
jumpMatch(forward):
  idx = matchSeqs.binarySearch(currentMatchSeq)
  idx >= 0  → 取相邻（越界则回绕到对端）
  idx <  0  → 当前匹配已被淘汰：按插入点沿方向取最近存活匹配（回退）
  positionOf(logEntries, target)  → listState.scrollToItem
```

`positionOf` 对显示视图按 seq 二分（子序列升序性质），未命中（被过滤/淘汰）返回 -1
跳过滚动但选中关系仍推进。

### 6.5 高亮：只构建可见行

命中片段用 `buildAnnotatedString` 叠加背景色 `SpanStyle`（普通匹配浅黄、当前匹配
琥珀），构建发生在 LazyColumn 的 item 组合里——**虚拟化保证只有屏幕内 ~30 行构建**，
与缓冲总量无关。无查询时直接渲染原文，零开销。

## 7. UI 交互层速览

| 能力 | 实现要点 |
|---|---|
| 跨行选中复制 | 整列表包 `SelectionContainer`（行 `fillMaxWidth` 短行空白可起选）；选中复制走 Ctrl+C。**框架边界**：虚拟化列表的字级选区只能覆盖已组合行、拖选无自动滚动，即"只能选可见区域"；选中行滚出组合后再扩展选区会触发 Compose 1.7 崩溃（见下"选区代际"） |
| 选区代际（防崩） | 视口版本号（firstVisibleItemIndex 每变 +1）与上次列表按下版本不一致 → 下一次主键按下时 `key()` 换代重建 SelectionContainer 并吞掉该次按下（`SelectionManager` 的 compareBy 查 `MutableLongIntMap` 缺 key 直接抛 `Cannot find value for key N`）。换代推迟到按下而非滚动瞬间——滚动瞬间换代会把滚动条拖拽等进行中的手势打断 |
| 行区间选择 | 「行选」开关（方案 A，跨视口整行选择的正解）：点击行设锚点、Shift+点击扩展端点，seq 区间（过滤视图内）整行高亮；Ctrl+C / 右键「复制选中行」复制区间全文，Esc 清除；主键按下在 `PointerEventPass.Initial` 遍历消费、阻断字级手势 |
| Ctrl+滚轮缩放 | 9~20sp 每档 1sp，消费滚轮事件避免列表同时滚动；指针 Ctrl 判断用 skiko 扩展 `pointer.isCtrlPressed`（1.7.3 无 `KeyboardModifiers.isCtrlPressed`） |
| 右键菜单 | `onPointerEvent(Press)+isSecondaryPressed` 记录点击点，`Popup(TopStart, offset=px)` 固定向下展开（DropdownMenu 定位算法会向上翻折）；「复制日志」= 过滤视图全文写剪贴板；「清空日志」= `clearDisplay()`；`LocalTextContextMenu provides 空实现` 抑制 SelectionContainer 自带的默认「复制/全选」菜单 |
| 滚动条 | `VerticalScrollbar` + `rememberScrollbarAdapter(LazyListState)`，hover 时 12dp 轨道淡色底 |
| 自动滚动 | 稳态（淘汰==新增）下列表 size 不变，跟随由**累计接收数**驱动；高频下 `scrollToItem` 不用动画 |
| 计数行 | 「过滤后 N · 全量 M 条 · 缓冲 x/8192 KB」——过滤强度与内存占用实时可见 |

## 8. 关键设计决策一览

| 决策 | 选择 | 理由 / 放弃项 |
|---|---|---|
| 容量管理 | 字节预算环形缓冲 | 条数上限防错了东西；LazyColumn 虚拟化下唯一约束是内存 |
| 过滤位置 | 全量存储 + 展示层派生视图 | 前置过滤无法重滤已显示内容；被过滤行会永久丢失 |
| 匹配/定位锚 | 单调 seq | 下标随淘汰漂移；内容 key 撞重复行崩溃 |
| 重滤线程 | 主线程同步 | 2 万条零 regex 毫秒级；与 flush 同线程顺序执行，免并发同步 |
| UI 状态容器 | SnapshotStateList | flush 只做增量 add/remove，不随总量整表重建 |
| 背压策略 | channel 1024 DROP_OLDEST + 攒批 150ms | 丢旧留新，UI 永不反压进程 |
| 进程清理 | awaitClose + destroyForcibly | 取消即杀，阻塞读立即返回，无僵尸 adb |
